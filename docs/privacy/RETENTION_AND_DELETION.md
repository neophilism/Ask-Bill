# Data minimization, retention and deletion — Ask Bill

The [machine-readable inventory](DATA_FLOWS.json) describes implemented application paths, their default enablement, the records actually written, retention enforcement, and the tests that exercise them. Its `implementation` field describes code; `liveAcceptance` separately describes external evidence. Provider adapters and local PostgreSQL/HTTP acceptance tests do not establish a live deployment, provider retention configuration, or completed deletion outside this application.

All optional AI, speech, transcription, publishing and official-import features default off. A credential alone enables none of them. The explicit local demo opens no database or live provider. Hosted application startup requires an independently configured publisher, private database and restricted runtime role. See [application configuration and activation](../ops/APPLICATION_RUNTIME.md) for the deployment controls.

## Reading, page state and explicit exports

Public source reading and the guided learning route require no account or microphone. Source responses use `no-store`; each version lookup checks the active publication. The application creates no visitor behavioral profile and does not write raw IP addresses to its data tables. The enhanced source search runs locally. Its no-JavaScript GET fallback sends a bounded search query to this server, where it is used only for that request. A query in a URL may still appear in browser history or hosting access logs: operators must omit query strings and verify the hosting log policy separately.

The reader stores only reading level, text size and validated provision bookmark IDs in browser `sessionStorage`. Questions, answers, session credentials and microphone data are excluded. Up to twenty displayed question/answer entries are held in page memory until cleared, evicted, or the page is unloaded. Server session expiry does not remotely erase a displayed page. Clear history removes page history and requests server-session erasure; Clear session also removes preferences. If the network deletion fails, the interface shows an explicit retry and retains the pending erasure capability rather than claiming server deletion succeeded.

Sharing uses an exact source/version/section link. A conversation download deliberately includes the questions and displayed answers the reader chooses to export. An offline source file contains public text only, no private question history and no executable scripts; it identifies itself as a snapshot that may later be withdrawn or superseded. User-saved files and browser history are outside remote application deletion. The [reader state implementation](../../packages/ui/reader/client-core.mjs) and [interactive browser acceptance](../../tests/browser/test_interactive_reader_browser.py) cover these boundaries.

## Anonymous question sessions and replay

An adult or 13–17 reader explicitly starts a question session. The server stores random capability and CSRF hashes, age band, epoch, expiry and request count; it does not require name, email or date of birth. Hosted cookies are Secure, HttpOnly and SameSite. Under-13 requests create no free-input session and lead to guided learning.

Raw questions exist only in the current server request and the reader's page memory. They are not written to application database tables, ordinary logs, or the replay record. With AI disabled, the server can return exact source quotations without a model request. With AI enabled, the current question and selected public evidence go to the configured generation provider, and a separate configured model reviews the held draft. The application releases validated segments, not the raw provider stream. An operator's `ASK_BILL_PROVIDER_DATA_PROTECTION=verified` setting records an activation decision; it is not itself evidence of a vendor's retention or child-data policy.

The [PostgreSQL session store](../../packages/sessions/pg-store.mjs) holds at most ten accepted answers for each session as AES-256-GCM ciphertext. Associated data binds each record to its publisher, session capability hash and answer ID. The replay payload contains accepted answer segments and source identity, not the raw question, microphone recording or transcription result. Requests are rejected at the 30-minute session expiry, even if expired rows have not yet been physically deleted.

Clear session deletes the active session in its tenant transaction and cascades its answer rows immediately. It also aborts in-flight generation, transcription and speech; a late result cannot restore an erased or replaced session. The running web process attempts cleanup every minute, deleting at most 100 expired sessions per pass; session creation also removes a bounded expired batch. A backlog or stopped process can delay physical cleanup, while expiry continues to deny access. Do not interpret a 30-minute capability lifetime as a hard promise that every database or backup copy disappears at that instant.

Daily quota rows contain publisher, calendar day and aggregate count only. They intentionally survive session recreation and erasure so clearing a session cannot reset the publisher's shared request ceiling. Cleanup removes days older than `CURRENT_DATE - 7`; calendar-day granularity can keep a row for up to eight days plus cleanup delay. They contain no user/session identifier, question, transcript or IP address. Defaults are request limits, not a dollar ledger.

[Real PostgreSQL acceptance](../../tests/postgres/application_session_store.mjs) verifies cross-tenant denial, concurrent session capacity, encrypted replay integrity, stale-epoch rejection, erasure cascades and quotas that survive recreated sessions. [Application security regression tests](../../tests/application-security.test.mjs) verify cancellation and suppression of late results.

## Recording, transcription and synthesized speech

Microphone recording is adult-only and begins after a Record gesture. A second action sends the recording for transcription. The browser captures at most 30 seconds; the server independently decodes supported recording containers through bounded FFmpeg pipes, verifies real decoded duration and strips container metadata. Client-reported duration is not trusted.

There is no application recording archive and no one-hour audio retention window. Audio and transcription text are not written to application storage. Mutable server input/normalization buffers are cleared after processing, including failed or cancelled transcription; transient strings and browser audio objects are released through their normal lifecycle. This describes application handling and does not promise physical erasure of every browser, operating-system or external-provider copy.

A returned transcript remains editable in the browser. Using it copies it into the question box; the reader must separately choose Ask Bill. Once explicitly submitted as a question, the ordinary question-flow rules apply. The application never submits a transcription automatically.

Speech sends only a server-authorized, validated answer segment to the configured speech provider. The API checks the current session epoch and exact publication before synthesis and rechecks them before delivery. Clear, replacement questions, source withdrawal and process drain prevent late audio from being delivered. Synthesized audio is transient and is not placed in application database or object storage. Provider retention and voice licensing remain independently verified activation requirements. Evidence is in [recording normalization](../../tests/recording-normalization.test.mjs), [push-to-talk](../../tests/push-to-talk.test.mjs), [audio adapter](../../tests/openai-audio-integrations.test.mjs) and application security tests.

## Publisher identity, originals and audit history

Publisher sign-in uses the actual [OIDC/PKCE adapter](../../packages/auth/oidc.mjs) with verified claims, browser-bound state, nonce, pre-enrolled issuer/subject hashes and fresh membership checks. ID/access tokens are not persisted or sent to public-client code. Five-minute login transactions are consumed atomically; abandoned expired transactions are pruned on subsequent login attempts. Publisher session capabilities expire after 30 minutes, logout deletes the active session, and expired rows are pruned on later session writes. Enrollment and membership records have their own publisher-controlled lifetime. Disabling an enrolled identity or removing membership denies subsequent use of its session even before capability expiry.

Private source uploads are bounded, scanned and stored in publisher-scoped S3-compatible quarantine. Independent byte-hash verification precedes promotion to immutable private-source storage; the worker reads and verifies the original again before extraction. Public packs are separate reviewed derivatives. The authenticated original-download route rechecks membership, pins the bill/version/raw digest and returns an attachment with a fixed safe filename, `private, no-store` and `nosniff`. A publisher can compare the extraction against the exact source bytes without a public bearer URL.

The seven-day quarantine lifetime remains an **operator lifecycle target**. No external bucket policy has been applied or independently verified by this code, and abandoned quarantine objects are not automatically deleted by the application. Private source retention, derivatives and backups require a publisher-approved archival purpose and deletion policy. Correction creates a new private extraction revision while preserving the original; withdrawal blocks public access while retaining provenance. Neither is source erasure or a recall of downloaded files.

Source extraction uses a separately probed containment boundary, no network, minimal environment and temporary storage. Workers receive only database, source-storage and optional Congress credentials; they do not receive OIDC, anonymous-session encryption, AI-generation or speech credentials. Durable requests contain source references and metadata, not provider secrets or reader questions.

Audit records contain publisher actor IDs, actions, source IDs/hashes and review check names. They exclude raw question text, microphone samples, source document bytes, credentials and session capabilities. Runtime credentials cannot alter enrollment or audit history, truncate tenant tables, or access migration metadata, including through inherited roles and column-level grants. The one-year audit target still requires an authorized archival/deletion job and backup policy; append-only runtime behavior is not an implemented annual purge.

## Flows that still require separate implementation or external policy

The child learning route is public and curated. There is no live under-13 free-input or parental-verification adapter. A checkbox or caller-provided boolean cannot activate child data transfer. The existing child predicate always denies live entry.

The feedback review/redaction helper is implemented as an isolated module, but the composed application has no durable feedback submission endpoint or sink. No automatic conversation feedback is collected. Its proposed 90-day lifetime is not an active deletion guarantee.

Source jobs and completion outbox events are durable and fenced. Without an explicitly injected idempotent delivery sink, the worker leaves outbox records pending; it never claims external delivery occurred. Operational retention remains unset until a recovery-safe archival/deletion policy accounts for retries, deduplication and restoration.

Application diagnostics use fixed startup/status metadata or an explicit narrow telemetry allowlist. Raw questions, source files, recordings, provider credentials and raw exception stacks are not logged by these paths. Hosting request logs and exported diagnostics are separate: their seven-day-or-less target needs a verified provider configuration. Public-source query strings must be omitted from those logs.

A complete deletion process must distinguish active application records, private objects and derivatives, provider-side copies, user exports and backups. Capability-proven session erasure handles the active session records only. Publisher-directed source deletion, provider deletion receipts, backup expiry, retention holds and restoration tombstones are not implemented end-to-end. A database restore must not silently reactivate erased sessions or withdrawn publications; operators must verify expiry and replay any applicable deletion/withdrawal records before making restored data public.

The earlier tenant-scoped expired-session primitive in [migration 007](../../migrations/007_retention.sql) remains available for the legacy reservation/session schema. It does not replace the anonymous runtime cleanup above or constitute full subject deletion.

Run `node tests/privacy.test.mjs` to validate the inventory, owning modules, exact test paths and persistence/default-enable distinctions. The listed functional tests provide their own local evidence; credentialed production acceptance, lifecycle policies and restoration evidence remain separate records.
